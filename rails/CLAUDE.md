## Commands

**Always** use `bin/rails generate` to create new files (controllers, views, models, migrations, et cetera).
**Never** write files by hand. Especially not @db/schema.rb. It will be updated using migration commands.

```bash
bin/setup                # Install dependencies, prepare the database, activate git hooks
bin/dev                  # Start dev server (Puma + Tailwind watcher via Procfile.dev)
bin/jobs                 # Start a Solid Queue worker
bin/ci                   # Full check suite (lint, security scans, tests, seeds)
bin/ci --with-system-tests   # The same, plus the browser suite
bin/rails test           # Run unit and integration tests
bin/rails test test/path/to/test_file.rb     # Run a specific test file
bin/rails test test/path/to/test_file.rb:42  # Run a specific test
bin/rails test:system    # Run system tests
bin/rubocop              # Lint
bin/rubocop -a           # Lint and auto-correct safe offenses
bin/brakeman             # Security scan
bin/bundler-audit        # Gem CVE check
bin/rails db:prepare     # Create, migrate, and seed the database
bin/rails db:migrate     # Run pending migrations
bin/rails db:rollback    # Roll back the last migration
bin/rails credentials:edit   # Edit encrypted secrets
```

## Checks

Run the full check suite with **`bin/ci`**, never `bin/rails test` on its own as
a gate. It covers setup, RuboCop, bundler-audit, importmap audit, Brakeman, the
test suite and seeds. Steps are defined in [config/ci.rb](config/ci.rb).

System tests are **excluded by default**. Add `--with-system-tests` whenever a
change touches views, Stimulus controllers, Turbo behaviour, the CSP or assets.

`bin/ci` also runs as a **pre-push hook** (`.githooks/pre-push`, activated by
`bin/setup`), so a push that would fail it is refused before it leaves the
machine.

After writing tests, check coverage in `coverage/index.html` (regenerated by `bin/ci`).

### Parallel tests

Unit and integration tests run in parallel above the threshold set in
[test/test_helper.rb](test/test_helper.rb). System tests are pinned to a single
worker in
[test/application_system_test_case.rb](test/application_system_test_case.rb)
because they drive a real browser against one server.

[config/database.yml](config/database.yml) sets no `host` in development and
test, so libpq connects over a Unix socket. Adding `host: localhost` makes it a
TCP connection, which negotiates GSSAPI — and macOS's GSS framework is not
fork-safe, so workers die with a SIGSEGV inside `connect_start` that reads like
a `pg` bug but is the connection setup. If a host is ever needed on macOS, pair
it with `gssencmode: disable`. Don't reach for `PARALLEL_WORKERS=1` or a raised
threshold to make the symptom go away.

## Code Style

- Follow Rails omakase conventions enforced by `rubocop-rails-omakase`; no custom
  overrides beyond the defaults (see [.rubocop.yml](.rubocop.yml)).
- Prefer Rails conventions over clever abstractions.
- **ALWAYS** use `bin/rails generate` when creating controllers, models,
  migrations, jobs, mailers or entire resources, with the relevant flags. Do not
  create these files by hand.
- Thin controllers — business logic lives in models, concerns or `app/services/`.
- Migrations must be reversible; never edit a migration that has been committed.
- Secrets go in Rails credentials, never in code or `.env` files committed to git.

### Comments

Do **not** elaborate in comments. Rationale, rejected alternatives and
narrative belong in the ADR, the PRD or the commit message — not in the code.

- At most, leave a reference to where the rule comes from (ADR, PRD, ticket).
- Cap a comment at 2–3 lines. A class-level comment gets one short paragraph,
  never a multi-section essay.
- Comment only what the code cannot say: a non-obvious constraint, a deliberate
  deviation, or the reference that explains where the rule comes from.

## Testing

- Framework: **Minitest** with fixtures (not FactoryBot); `fixtures :all` loads
  every fixture for every test.
- Integration tests get `SessionTestHelper` automatically (included via `on_load` hook):
  - `sign_in_as(user)` — creates a session and sets the signed cookie
  - `sign_out` — destroys the session and clears the cookie
- System tests use Capybara + Selenium.
- Write tests for new features. Prefer integration tests for request flows, unit
  tests for model logic. Plain Ruby service objects are unit-tested directly.

## Architecture Notes

- **Current**: `Current` (ActiveSupport::CurrentAttributes) holds request-scoped
  state. The session is stored at `Current.session`.
- **Sessions**: cookie-based with a signed, `httponly` `session_id` cookie. The
  `sessions` table stores active sessions per user.
- **Solid adapters**: Cache, Queue and Cable each use their own PostgreSQL
  database, configured in `config/database.yml`. In development they run inside
  the Puma process started by `bin/dev`.

### Controller namespacing


## Two-Factor Authentication

TOTP via `rotp`; the provisioning QR code is rendered with `rqrcode`.

- **Enrolment**: the user scans a QR code and enters a code to verify. The
  pending secret lives in the session until confirmed, then is persisted to
  `users.otp_secret`.
- **Login challenge**: when a user with `otp_secret` logs in,
  `SessionsController#create` stores the pending user id in the session and
  redirects to the TOTP challenge instead of issuing the session cookie. On a
  valid code, `start_new_session_for` is called normally.

## Content Security Policy

Enforced in every environment from `config/initializers/content_security_policy.rb`,
with every fetch directive set to `'self'`. Practical rules when adding to the
front end:

- **Everything must be same-origin.** No CDN scripts, external stylesheets, web
  fonts, remote images or iframes — they will be blocked. Vendor the asset into
  `app/assets` or `vendor/javascript` instead.
- **`script-src` uses `'strict-dynamic'`**, so the `'self'` allowlist is ignored
  and every `<script src>` needs the nonce. `content_security_policy_nonce_auto`
  gives it to the Rails tag helpers; hand-written `<script>` tags in views will
  not get one and will be blocked.
- **Never add a nonce to a directive that relies on `'unsafe-inline'`** — a nonce
  makes the browser ignore `'unsafe-inline'` for that directive.
- **Active Storage must stay in proxy mode** (`resolve_model_to_route =
  :rails_storage_proxy`). Redirect mode or an external service URL would move
  blobs off-origin and `img-src 'self'` would blank every uploaded image.
- **Check the browser console after touching the policy.** System tests catch a
  CSP that breaks the importmap (Turbo and Stimulus go down), but assert nothing
  about fonts or images.

## UI Conventions

- **All web UI must be built from Tailwind Plus components**, fetched through
  the `TailwindPlusServer` MCP server. Search it first whenever designing or
  updating a view; adapt the closest matching component rather than writing UI
  from scratch. See [app/views/CLAUDE.md](app/views/CLAUDE.md).
- **Use lucide icons** via `lucide-rails` instead of hand-drawn SVG. Verify an
  icon exists at https://lucide.dev/icons/ before using its slug in the helper.
- **Dark mode and mobile-first are mandatory.** Every page has four variants:
  light desktop, dark desktop, light mobile, dark mobile. Use Tailwind's
  responsive and `dark:` modifiers.

## Commits

- Work on a feature branch. Commit straight to `main` only when explicitly asked.
- Run `bin/ci` before every commit and ensure it passes (add
  `--with-system-tests` when the change can affect the UI).
- One logical change per commit. Never combine two features, or a feature and a
  fix, in the same commit.
- Keep commits small — up to roughly 100 significant lines. If larger, split
  the change into multiple sensible commits.
- The first line must be prefixed with one of `feat`, `fix`, `chore`, `docs`,
  depending on the purpose, and be no longer than 80 characters.
- The body is a bulleted list of changes, separated from the title by a blank
  line. It can be omitted for trivial changes.
